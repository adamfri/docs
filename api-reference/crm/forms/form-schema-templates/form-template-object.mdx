---
title: "Form Template Object"
description: "A form template is a reusable definition of a form's fields, steps, and settings."
icon: "cube"
---

A form template is a reusable definition of a form's fields, steps, and settings. It's used as the
source when creating a form. App owners define templates for their namespace in the app dashboard,
and this API retrieves them.

<Tabs>

  <Tab title="REST">

    <ResponseField name="id" type="string">

      Form template ID.

      **Read-only.**

    </ResponseField>

    <ResponseField name="namespace" type="string">

      Namespace that groups this template with the templates and forms belonging to the same app or use
      case, such as a bookings or pricing plans checkout. The value is defined by the app that owns the
      template in the app dashboard, and is the value you pass when retrieving form templates.

      Constraints: `minLength 10`, `maxLength 50`, `immutable`.

    </ResponseField>

    <ResponseField name="formFields" type="Field[]">

      Fields of the form, such as text inputs, and display elements, such as the submit button. Each
      step's layout places a field by referencing the field's `id`.

      Constraints: `maxItems 100`.

      <Expandable title="formFields properties">

        <ResponseField name="id" type="string">

          Field ID.

          The ID is stored in lowercase. Because the form's layout references each field by this ID, pass a lowercase GUID so that `id` and the layout's `fieldId` still match after the form schema is stored. IDs must be unique in the form.

          Constraints: `format GUID`, `immutable`.

        </ResponseField>

        <ResponseField name="hidden" type="boolean">

          Whether the field is hidden from submitters.

          Default: `false`

        </ResponseField>

        <ResponseField name="identifier" type="string">

          Identification for the field, describing its purpose. For example, `TEXT_INPUT` or `CONTACTS_EMAIL`.

          Set this to the known value for the kind of field you're creating.
          An unrecognized value, such as a custom string or a GUID, is dropped rather than rejected: the request still succeeds, but the field doesn't appear in the response's `formFields`, and neither the field nor its submitted values appear in the Wix dashboard.

          Several fields share a general-purpose `componentType`, so `identifier` is often the only value that distinguishes them.
          For example, both a short answer field and a long answer field use the `TEXT_INPUT` component, and are told apart by their `TEXT_INPUT` and `TEXT_AREA` identifiers.

          For the full list of known values, see [About Form Fields](https://dev.wix.com/docs/api-reference/crm/forms/form-schemas/about-form-fields).

        </ResponseField>

        <ResponseField name="fieldType" type="string">

          Field type.

          `INPUT` fields collect data from submitters and are configured in `inputOptions`.
          `DISPLAY` fields show information without collecting data and are configured in `displayOptions`.

          **Supported values:**

          - `UNKNOWN_FIELD_TYPE` — Unknown field type.
          - `INPUT` — Input field that collects data from users.
          - `DISPLAY` — Display field that shows information without collecting input.

        </ResponseField>

      </Expandable>
